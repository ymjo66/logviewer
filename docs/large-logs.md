# 대용량·다중 로그의 메모리 문제

## 1.0.3 EXE: 네이티브 파서와 디스크 페이지

EXE는 브라우저의 파일 전체 버퍼와 모든 로그의 메모리 인덱스 대신 C# `DiskLogEngine`을 사용합니다. HTML 버전에는 이 엔진이 없으며 아래의 이전 브라우저 구조를 사용합니다.

1. Windows 파일 선택/드롭으로 등록한 파일만 읽습니다. 원본 전체를 1MiB 버퍼로 실행별 임시 폴더에 복사하고 복사 도중 원본이 변경되면 실패로 보고합니다.
2. BIN을 4MiB 청크로 스캔합니다. 청크 경계를 연결하고 모든 유효 패킷을 인덱스로 저장합니다. 각 인덱스는 원본 위치 8바이트·스키마 ID 4바이트·길이 4바이트·TimeUS 8바이트입니다. LOG는 UTF-8 행 경계를 연결해 원본과 행 위치를 보존합니다.
3. 원본 필드는 8MiB 메모리 매핑 창에서 필요한 만큼 해석합니다. 스키마 변경·32개 원소 배열·문자열·정밀도를 잃을 수 있는 64비트 정수를 유지합니다. 부동소수점은 전송 중 재반올림되지 않게 원래 비트로 전달합니다.
4. 기존 `analysis.js` 규칙은 별도 Worker에서 실행합니다. 원본을 128행 페이지로 읽고 타임라인도 생성 중 디스크에 기록합니다. 주 화면·Worker 각각 추정 16MiB LRU 페이지 캐시, 쓰기 중 최대 4페이지를 사용합니다. 전체 앱 메모리는 이 값보다 크며 일부 진단용 중간 배열·차트 데이터·메타데이터는 계속 메모리를 사용합니다.
5. BIN 필드 조회는 시간 정렬이 검증된 테이블에서 시간 인덱스로 범위를 찾습니다. 정렬되지 않았으면 전체 인덱스를 순회합니다. 원본 전체 또는 조회 범위의 모든 수치로 통계를 계산하고, 화면에는 600개 구간의 첫값·끝값·최소·최대·결측 표시를 반환합니다. 확대하면 원본에서 다시 조회합니다.
6. 재분석은 별도 결과 세대에 저장한 뒤 전환합니다. 실패하면 이전 결과를 유지합니다. CSV는 기존 선택 열과 값을 그대로 사용하되 128KiB 정도씩 기록하고 성공 시 최종 파일로 교체합니다.

`%LOCALAPPDATA%/LogViewer/disk-cache/<실행 ID>/`에 원본 복사본·인덱스·분석 결과가 생깁니다. 원본 크기 합계 외에 패킷당 24바이트와 JSON 분석 결과, 재분석 작업 공간이 필요하므로 단순히 원본 크기만큼의 여유로는 부족할 수 있습니다. 정상 종료 또는 목록 삭제 시 해당 캐시를 삭제하며 원본은 건드리지 않습니다. 비정상 종료 시 남은 캐시는 모든 창을 닫은 뒤 이 폴더에서 정리할 수 있습니다. 네트워크 서버·GPU는 필요 없습니다. 네이티브 파서가 모든 WebView2 메모리 한계를 제거하거나 무제한 처리를 보장하지는 않습니다.

### 검증 범위

- `tests/native-disk.cjs`: 네이티브와 기존 파서의 모든 행·필드를 엄격 비교합니다. 청크 경계·스키마 변경·배열·64비트·-0/NaN/Infinity, 전체/구간 통계, 필드 목록과 인스턴스, 실패한 재분석의 결과 보존을 검사합니다.
- 실제 `00000459.BIN`: 585,737개 데이터 패킷, 4,725,714개 필드가 일치했습니다. FMT 포함 총 패킷은 585,921개, 탐색기 목록은 122개 메시지/인스턴스와 1,084개 필드입니다.
- `tests/native-adapter.cjs`: 다섯 로그 시나리오의 전체 분석 결과·시각·소티·진단과 선택 열 CSV가 기존 구현과 일치합니다. 페이지 교체 및 임의 타임라인 수정도 검사합니다.
- 약 845MB 합성 BIN의 10,690,561패킷 네이티브 인덱스와 필드 조회를 검사했습니다. 실제 BIN 하나를 58회 등록하여 약 1.20GB/33,983,418패킷의 인덱스를 함께 유지하는 별도 테스트도 수행했습니다. 이는 네이티브 엔진 테스트이며 GUI 전체 분석의 RAM 측정이나 사용자의 서로 다른 대용량 58개 성공 보장은 아닙니다.
- 실제 EXE에서 BIN+LOG를 함께 불러오고 3,723행의 텔레메트리 CSV 저장을 확인했습니다. 파일 시스템 권한·디스크 부족·원본 변경 등의 실패는 여전히 가능하며 실패한 파일을 결과 목록에서 확인해야 합니다.

## 1.0.2까지의 브라우저 구조 (이전 기록)

아래 내용은 1.0.2까지의 구조와 현재 단일 HTML에 해당합니다. BIN은 모든 패킷을 스캔하고 전체 인덱스·필드 정의·분석 결과를 보관한 뒤, 비활성 로그의 원본 바이트 캐시를 해제합니다. 선택하면 처음 첨부한 File 참조로 원본 바이트를 다시 읽습니다. 요약 데이터만 불러오거나 패킷을 제외하는 방식이 아닙니다.

선택·추가·전체 재분석은 순서대로 처리하고 목록 삭제 시 차트 참조와 원본 캐시도 해제합니다. 원본의 별도 디스크 복사본을 만드는 기능은 아직 없으므로 사용 중 원본 파일을 이동·수정하거나 저장 장치 연결을 해제하지 마세요. 이 캐시 해제는 BIN에 적용되며 텍스트 LOG는 열 데이터를 유지합니다.

선택된 원본과 현재 읽거나 분석 중인 원본, 모든 파일의 인덱스·분석 타임라인은 여전히 메모리를 사용합니다. 선택 전환 중에는 두 원본이 잠시 함께 존재할 수 있습니다. 모든 용량·개수의 성공을 보장하지 않습니다. 메모리 오류 후 비교할 때는 기존 Log Viewer 창을 모두 종료한 뒤 수정본을 실행하세요.

58·101·150개 예시 로그, 150개 BIN 원본 캐시 해제, 선택 전환·전체 재분석을 검사합니다. 실제 00000459.BIN은 캐시 해제·재읽기 후 모든 원본 값도 비교합니다. 사용자의 실제 대용량 54개/58개 전체를 검증한 결과는 아닙니다.

## 수정 전 확인한 원인

`src/js/ui.js`의 readSingleFilePromise는 BIN을 FileReader.readAsArrayBuffer로 한 번에 읽습니다. `src/js/parser.js`는 모든 패킷을 행 객체로 해석하여 보관합니다. 텍스트 LOG는 전체 문자열 및 split한 행 문자열도 필요합니다. `analysis.js`는 정렬·필터링용 배열과 분석 타임라인, 자기장 계산 배열 등을 만들고 차트는 별도의 좌표 데이터를 구성합니다.

따라서 디스크의 800MB와 메모리 사용 800MB는 다릅니다. 필드 수·패킷 수·배열 메시지 비율에 따라 훨씬 커질 수 있습니다. 작은 파일 여러 개는 파일마다 읽기·정렬·그래프 생성 시점이 나뉘어 순간 최대 사용량이 다릅니다. 다중 로그도 원본 해석 데이터를 계속 보관하므로 무제한으로 안전하지 않습니다. 실제 문제의 800MB 파일을 제공받아 재현한 결과는 아니며 메모리 부족 외 손상 패킷·매우 긴 배열 연산 등의 가능성도 남아 있습니다.

## EXE면 해결되는가?

현재 Windows EXE는 WebView2에서 동일한 JavaScript 분석 코드를 실행합니다. x64 EXE여도 브라우저 렌더러의 메모리 제한과 시스템 메모리 압박이 사라지지 않습니다. HTML을 EXE로 포장하는 것만으로 해결을 보장할 수 없습니다. 약 845MB 합성 BIN은 검증했지만 모든 실제 800MB 로그를 검증한 것은 아닙니다.

## 이번에 적용한 개선

BIN은 8MiB 청크로 읽으며 모든 원본 바이트를 청크 배열에 보관합니다. 패킷 위치를 수치 배열에 저장하고 행·필드는 필요할 때 해석합니다. 원본을 요약하거나 패킷을 건너뛰지 않습니다. LOG 텍스트는 청크별로 행을 해석하고 모든 값을 열 단위 수치 배열·문자열 사전에 보존합니다. 분석 타임라인도 열 단위로 저장하고 차트용 전체 좌표 객체 배열 복제를 줄였습니다. 읽기 진행률을 표시하고 청크 사이에 화면 처리 기회를 제공합니다.

약 845MB(844,554,329바이트) 합성 BIN의 10,690,561패킷을 보존하는 검증과 1천만 레코드 사용자 지정 차트의 통계를 검증했습니다. 원본 배열의 짧은 피크·64비트 정수·스키마 변경·청크 경계도 검사했습니다. 실제 00000459.BIN의 585,737개 데이터 패킷 / 4,725,714개 필드 값, 3,602개 분석 타임라인 행 및 진단·소티가 기존 파서와 일치했습니다. FMT 패킷은 데이터 행 수와 별도로 집계됩니다. 테스트 환경과 PC 성능에 따라 속도·메모리는 달라집니다.

선택된 원본 바이트는 메모리에 보관하므로 약 800MB 파일을 선택하면 약 800MB 이상의 실제 메모리가 필요합니다. 비활성 BIN 원본 캐시는 최신 변경에서 해제합니다. 1천만 점 필드의 전체 통계 계산은 시간이 걸릴 수 있습니다. 디스크 복사본 캐시 및 Worker 분리는 아직 적용하지 않았으며 원본을 서버에 올리지 않습니다.

## 후속 개선 가능 항목 (아직 미구현)

1. BIN을 8~16MiB 등 작은 청크로 읽고, 청크 경계에서 잘린 패킷을 다음 청크와 연결합니다. 파일 전체를 펼친 버퍼를 계속 보관하지 않습니다.
2. 1차 스캔에서 메시지·시간·파일 위치 인덱스만 만듭니다. 필드를 선택하거나 구간을 확대하면 그 부분만 다시 읽고 해석합니다. 모든 필드·모든 원본을 객체로 상시 보관하지 않습니다.
3. 필요한 수치 열은 TypedArray로 저장하고 시간축을 공유합니다. 전체 구간 차트에는 최소·최대 피크 요약을, 확대 구간에는 원본을 사용합니다.
4. Web Worker에서 파싱하고 진행률·취소를 제공합니다. Worker만 추가하고 데이터를 복제하면 메모리가 늘 수 있으므로 버퍼 소유권 이동과 저장 구조 개선을 함께 적용합니다.
5. 원본 CSV 내보내기는 원본 파일을 다시 스트리밍해 처리하여 데이터 손실 없이 저장합니다. IndexedDB/OPFS 디스크 캐시는 브라우저·로컬 파일 정책과 저장 공간을 확인한 뒤 선택합니다.

이 방법은 단일 HTML에도 적용할 수 있습니다. Windows EXE에서는 추후 네이티브 파서와 디스크 기반 저장소를 추가하는 대안도 있습니다. RAM 증설·64비트 브라우저·불필요한 탭 종료는 여유를 줄 수 있지만 구조적 해결은 아닙니다. 임의 바이트 단위 파일 분할은 FMT/단위/인스턴스 정의를 잃을 수 있으므로 권하지 않습니다.
