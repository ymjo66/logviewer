# 대용량 로그: HTML과 EXE의 공통 처리 구조

1.0.3 수정 EXE는 HTML과 동일한 브라우저 파서와 메모리 관리 경로를 사용합니다. C# 호스트는 창 제어·자동 업데이트만 담당합니다. 파일 선택과 드래그·드롭은 WebView2의 File API로 처리하며 네이티브 디스크 인덱스·분석 결과 캐시를 만들지 않습니다.

## 파일 읽기와 메모리

- BIN은 8MiB 청크로 읽고 모든 유효 패킷의 위치·스키마를 유지합니다. 원본 바이트에서 필요한 필드를 해석하므로 수백만 행 객체를 상시 보관하지 않습니다.
- 분석 타임라인은 열 단위 수치 배열·문자열 사전으로 저장합니다. 비활성 BIN의 원본 바이트는 해제하고 선택 시 처음 첨부한 File 참조로 다시 읽습니다. 모든 파일의 인덱스·필드 목록·분석 결과는 계속 메모리에 남습니다.
- 텍스트 LOG는 청크별로 해석하고 열 데이터를 메모리에 보관합니다. 비활성 원본 바이트 해제와 같은 방식으로 텍스트 열 데이터가 사라지는 것은 아닙니다.
- 필드·센서 인스턴스 목록은 원본 바이트 해제 전에 저장하므로 비활성 BIN 목록을 표시할 때 해제된 원본을 읽지 않습니다.
- 선택 전환 중에는 두 원본이 잠시 함께 존재할 수 있습니다. 파일 합계 용량이 RAM 사용량과 같지는 않으며 패킷·필드 수와 로그 종류에 따라 메모리 사용량이 달라집니다.

로그 사용 중에는 원본을 이동·수정하거나 저장 장치를 분리하지 마세요. 원본을 서버에 업로드하지 않습니다. 패킷·필드·진단 규칙은 생략하지 않으며 차트용 점만 피크를 보존해 줄입니다. 통계는 조회 범위 전체 수치를 사용합니다.

## EXE의 로컬 저장 공간

수정 EXE는 로그용 `disk-cache`를 새로 생성하지 않습니다. 실행 리소스 추출, WebView2 프로필, 업데이트 파일과 진단 로그 등 앱 운영에 필요한 저장 공간은 계속 사용합니다. 이전 디스크 엔진이 남긴 파일은 자동 삭제하지 않습니다. 구형 EXE의 참고 코드와 회귀 테스트는 저장소에 유지하되 디스크 엔진은 배포 EXE에서 컴파일하지 않고 JavaScript 어댑터도 배포 HTML에 포함하지 않습니다.

동일한 코드 경로를 사용해도 WebView2·브라우저 버전, PC 메모리, 원본 저장 장치와 백그라운드 작업에 따라 성능 차이가 날 수 있습니다.

## 검증 범위

- 기존 청크 경계·스키마 변경·배열·64비트 정수와 분석·차트·CSV 회귀 테스트를 유지합니다.
- `tests/multi-upload.cjs`는 58·101·150개 합성 로그, 150개 BIN 원본 캐시 해제·필드 목록·선택 전환·재분석과 읽기 오류를 검사합니다.
- `tests/large-parser.cjs --stress --plot`은 약 845MB 합성 BIN과 1천만 행 필드 차트를 검사합니다. 일반 테스트에 이 대용량 검사가 자동 포함되지는 않습니다.
- Windows EXE의 `--browser-self-test <JSON 경로>`는 실제 WebView2에서 BIN 파일 입력, LOG 드래그·드롭, 원본 캐시 해제·로그 전환·필드 목록·차트·CSV·재분석과 창 제어 초기화를 검사합니다.
- 사용자는 HTML에서 실제 로그 112개·합계 약 23GB의 로딩 성공을 보고했습니다. 이는 해당 PC·로그 조합의 실사용 결과이며 새 EXE에서 같은 112개를 재현 측정한 결과나 모든 환경의 처리 한도는 아닙니다.
